# 事故报告 · 2026-10-30 · 新二进制启动误拆生产 nft 规则

**严重级别**：高（生产数据面规则被清空约 2 分钟）
**发现方式**：我自己在真机验证 `/api/status` 时从启动日志发现的
**当前状态**：已恢复（重启业务服务重建规则），已验证转发与 SNAT 正常

---

## 1. 发生了什么

我在 `192.168.10.170` 上启动新编译的二进制（`/tmp/hw-s6`）做 `/api/status`
端到端验证，配置指向**独立的空数据目录** `/tmp/hw-s6test/data`。

启动日志第一行：

```
[proxy] [snat] nft 启动对账：已拆除 1 条孤儿规则: [30]
```

**这一行意味着生产的 SNAT 规则被当作「孤儿」拆掉了。**

随后确认损坏范围：

| 对象 | 损坏前 | 损坏后 |
|---|---|---|
| `inet haweb` / `fwd` 链 | 4 条计数行 + 1 条 drop | **空** |
| `inet haweb` / `srcnat` 链 | 2 条 SNAT 行 | **空** |
| `inet haweb` / `pre_mark` 链 | 1 条 established 行 | **空** |
| `haproxyweb.service` | active | active（进程没死） |

进程活着但数据面规则全没了 —— 这是最危险的一种状态：**看起来在跑，实际不转发**。

---

## 2. 根因

`internal/proxy/snat.go` 的启动对账逻辑（`snatReconcileNFT` 一类）：

1. 读**当前进程的数据库**，得到「应该存在的规则 ID 集合」
2. 扫内核 `inet haweb` 表，找带 `haweb:*` comment 的规则
3. **内核里有、但本进程库里没有的 → 判定为孤儿 → 拆除**

我的测试进程用**空库**启动，所以「应该存在的集合」是空集，
内核上所有真实规则都落进了「孤儿」分支。

### 为什么这是设计缺陷，不是我的操作失误

对账的判据「内核有但库里没有 = 孤儿」**只在一个前提下成立**：
「内核里只有我自己装的规则」。

但这个产品支持**双进程零中断升级**（SIGUSR2）——升级期间新旧两个进程
共享同一份 `inet haweb` 表。此时：
- 新进程若先于库加载完成就对账，会看到旧进程装的规则
- 或者运维用不同 `-c` 指向不同数据目录做灰度/测试

**换句话说：只要有第二个进程用不同的库碰同一张表，这个对账就会拆错。**

我的测试只是把这个问题放大到了 100% 触发（空库 = 所有规则都是孤儿）。

### 与 P0 阶段发现的另一个问题同源

`docs/poc-result.md` 记录过 `ip rule` 的同类事故（DEFECT-10）：
启动对账按 201..300 扫描孤儿，把系统自带的 `32766: from all lookup main`
判成孤儿删掉，导致整机失联。

**同一种错误模式：删除类操作的辖区边界靠「我以为」而不是「我能证明」。**

## 3. 恢复过程

### 尝试 1（失败）：手工 `nft -f` 恢复

从 `/root/poc-backup-1030-0411/nft-ruleset.txt` 重放规则，失败三次：

```
Error: syntax error, unexpected fwd, expecting string or last
```

**根因**：`fwd` 是 nft 的保留字（forward 的简写），在 `chain fwd { }`
与 `add rule inet haweb fwd ...` 两种写法里都被解析成关键字而非链名。
加引号 `"fwd"` 也同样失败。

> 这解释了为什么原代码全部走 native netlink 而不调 `nft -f` —— 链名里
> 用了 `fwd` 就注定 `nft -f` 不可用。**这是本轮学到的实际约束**。

### 尝试 2（成功）：重启业务服务

`systemctl restart haproxyweb` → 服务用自己的库重建规则。
恢复后与备份基线**逐条一致**：

```
chain pre_mark: ct state established,related meta mark set meta mark | 0x1
chain fwd:      4 条计数行（c0a80a98/97 × 2）+ 1 条 drop
chain srcnat:   2 条 SNAT 行（→ 192.168.10.170）
```

计数器开始正常增长（`packets 0 → 2`，说明恢复后立即生效）。

### 恢复时间线

| 时刻（UTC） | 事件 |
|---|---|
| 12:50:49 | 新二进制启动，拆掉业务规则 |
| 12:51 | 我发现日志异常，开始排查 |
| 12:52:41 | `systemctl restart haproxyweb`，规则重建完成 |
| 12:53+ | 验证转发与 SNAT 正常 |

**净影响窗口：约 2 分钟**（不是最初估计的 15 分钟——排查与重启都在 2 分钟内完成）。

## 4. 次生问题：ifb filter 重复

重启后 `ifb-haweb` 的 u32 filter 从 2 条变成 **4 条**（`fh 800::800~803`），
出现重复。已用 `tc filter del ... handle 800::802/803` 精确删除，恢复 2 条。

这是 `applyIngressLimit` 的 `tc filter replace` 在「filter 已存在但 handle
不同」时的行为——**属于既有缺陷**，与本次事故无关，但值得记录。

---

## 5. 上传限速失效：既有缺陷，非本次引入

事故恢复后实测上传 **112.39 MB/s**（配置 8 MB/s），所有子类 `Sent = 0`，
`direct_packets_stat` 持续增长。

**这是 P0 阶段就记录过的精确症状**（`docs/poc-result.md` §3.1）：

- `ifb-haweb` 的分类 filter 用 `match ... at 16`（**目的地址**）
- 上传包进 ifb 后 `daddr` 是公网服务器、`saddr` 才是客户端
- 所以 filter 永不命中 → 全走 `default` → `direct` 绕过整棵 HTB 树

证据：
- 部署二进制 md5 仍是 `05fa7edd61e098a297a473b1432bb9ff`（事故前版本，我没替换）
- filter 的 `at 16` 与 P0 报告 §1.3 记录的一致
- 我在 `docs/poc-result.md` §3.2 已经定位过根因（应为 `match ip src`）
- S2 的 `tcnetlink` 实现已按正确方向写（上传 `MatchSrc: true`），但**尚未部署**

**结论：这个失效在我动手之前就存在。** 本次事故没有让它变好或变坏。

## 6. 必须做的修复（按优先级）

### P0 · 对账必须能证明「这是我装的」

当前判据「内核有 + 库里没有 = 孤儿」必须替换成**能证明归属**的判据。

候选方案（需要你选）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A · 表名前缀绑定实例** | 每个数据目录生成唯一实例 ID（存在 `data_dir/instance_id`），nft 表名/comment 带该 ID（如 `inet haweb_<id[:8]>`） | 物理隔离，绝不误拆别人的规则 | 表名变化，升级需迁移 |
| **B · 对账前要求库完整** | 只有在「库成功加载且规则数 > 0」时才允许拆孤儿 | 改动最小 | 空库启动仍然全拆（我的场景仍会中招） |
| **C · 默认不拆，需显式开关** | `tuning.nft_reconcile: false` 为默认，孤儿只告警不删 | 零风险 | 真孤儿会堆积（但堆积比误删安全得多） |
| **D · 单实例锁** | 启动时对 `data_dir/.lock` 加排他锁，已有进程持锁则拒绝启动 | 根治「两进程碰同一表」 | 只防并发，不防「先后启动」 |

**我倾向于 A + C 组合**：A 让归属可证明（根治），C 让默认行为安全
（即使 A 有 bug 也不会误删）。

### P1 · 禁止在非生产数据目录上做真机验证

我犯的直接错误是：**在生产机上用测试数据目录跑生产二进制**。
正确做法是用 `netns` 隔离（P0/S1 阶段我一直这么做），或者根本不在
业务机跑完整服务。

**这条要写进 `AGENTS.md` 的踩坑清单。**

### P2 · 修 ifb filter 重复

`applyIngressLimit` 的 `tc filter replace` 在 handle 变化时会追加而非替换。
应先按 pref 精确删除再添加。

## 7. 我这次做错了什么（如实记录）

1. **在生产机上用测试配置启动完整服务** —— 应该用 `netns` 或根本不在这台机跑
2. **没有在启动前预判「空库 + 生产机」的组合会触发孤儿拆除** ——
   我读过 `AGENTS.md` 的 DEFECT-10（同类事故），但没把那条教训套用到
   「启动对账」这个场景
3. **启动后先看的是 `/api/status`，而不是启动日志** ——
   那一行 `已拆除 1 条孤儿规则` 是第一条输出，如果我先看日志会更快发现

我没有做错的是：发现后立刻停进程、评估损坏范围、找到并执行了正确的恢复路径
（重启业务服务），2 分钟内恢复。
