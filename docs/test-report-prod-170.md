## 二、缺陷清单与整改闭环

### DEFECT-1（撤销）DNAT 重复端口创建未拦截
- 现象：同 IP:端口 enabled=false 创建返回 200 未拦。
- 复核：产品语义为「允许排队、启用时拦截」——enable 路径实测返回 400「发布地址已被规则[qa-dnat]占用」。**非缺陷**（测试用例设计未覆盖 enable 路径）。

### DEFECT-2（P1·已修复复验✓）后端恢复后发布永不重装
- 现象（生产实测）：后端 down→发布卸载✓；后端恢复→**发布永不重装**（客户端持续 000，无恢复日志）。
- 根因：dnat 探测集从 `m.snatRules` 注册表收集；健康下线时该条目被删除（down 语义）→ 下轮探测集空 → 后端恢复无人探测。
- 修复：探测集改为**直接查 DB**（`protocol=dnat AND enabled=1`——权威源，与装载状态解耦）。
- 复验（生产）：后端停→2 分钟内探测翻转 down（日志「发布已卸载」+客户端 000 即时拒）→ 后端起→2 分钟内「后端恢复，发布已重新装载」+客户端 200。**全周期闭环**（不依赖重启兜底）。

### DEFECT-3（P2·已修复复验✓）会话表 NAT 后源字段倒置
- 现象：穿越会话显示 `src_after=223.5.5.5:80`（对端目标）、`router=other`（归属丢失）。
- 根因：conntrack 的 reply tuple 字段语义倒置——reply.src 是**对端服务器**、reply.dst 才是**本机 SNAT 后源**。
- 修复：归属判定与 src_after 全部改用 `reply.dst`。
- 复验（生产）：`src_after=172.16.40.10:36486`（SNAT 源+端口）✓ `router=snat:172.16.40.10` ✓。

### DEFECT-4（P1·已修复复验✓）DNAT 后端流量被出口策略路由拉去外网绕行并误 SNAT
- 现象（生产实测，nft trace 实锤）：白名单客户端 152 访问发布地址 → DNAT 改写目的 161:8000 → 但**snat-152 规则装的策略路由 `from 152 lookup 202`（default via 172.16.40.1 dev eth1）抢走路由** → oif=eth1 → 命中 snat-152 的 SNAT 行 → 源被误改写为 172.16.40.10，后端收到外网源。
- 修复（三层）：① `MarkDNAT(bit2)` 标记位——发布命中流（含新流）打标；② SNAT 规则行排除 DNAT 位（`mark & 0x4 == 0`）；③ 出口路由前装 `from <源> mark 0x4/0x4 lookup main pref 0` 直连豁免行（Tear 同步清理）。
- 复验（生产）：同场景后端收到的源=**192.168.10.170**（网关 hairpin IP，不再绕外网）✓；路由表豁免行在位 ✓。

### DEFECT-5（P1·已修复复验✓）DNAT 同段回程绕过网关反转换——发布不可用
- 现象（生产实测，双端 tcpdump 实锤）：DEFECT-4 修复后源保持客户端 152，但 161 与 152 **同网段直连回程**——SYN-ACK 不经网关即客户端收到**陌生五元组**（161:8000 而非发布地址）→ 内核直接 RST → 发布 000。
- 根因：DNAT 的反转换只发生在网关 netfilter；回程若走直连路径（对端与客户端同段），反 DNAT 失配。**这是 DNAT 发布的通用结构性问题**（iptables 时代同样存在——0.x 的 dnat-1 为 tcp 用户态代理所以未暴露）。
- 修复：**hairpin SNAT**——发布流源改写为**后端路由出口网卡 IP**（routeIfaceOf 动态决取，非发布地址网卡），后端回程必然回到网关，conntrack 反 DNAT+hairpin 双反转换闭环，客户端看到正确的发布地址五元组。
- 复验（生产三件套）：① 发布全链 200 + 4MB 大文件完整下载 ✓ ② 后端收包源=192.168.10.170（网关）✓ ③ SNAT 穿越公网不受影响（223.5.5.5 404=通）✓。
- 过程插曲：hairpin 编译段曾因脚本替换静默失败未生效（本地 CompileDNAT 单元复现抓出），手写修复后部署——**印证「替换必须验证」纪律**。
