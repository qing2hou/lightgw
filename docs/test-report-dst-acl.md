## 4. 环境残留观察项（非缺陷）

测试后 161 上存在 `ip rule from 192.168.10.162 lookup 201/203` 两条策略路由残留，路由表内容已空、无转发影响。成因：ip rule 无 comment 标记，`PurgeOrphanSnatRules` 启动对账只按 iptables comment 清 iptables 行、不覆盖 ip rule；遗留规则 #60（off 态）停用时也不清其 ip rule——**该行为在上一轮全场景测试（test-report-scenarios.md）已存在，非本功能引入**（表 202 同型残留可复现）。处置建议已单列，如需可加「停用/删除时清本表全部 ip rule + 启动对账扫描无主表」的收尾清理。

## 5. 独立评审与缺陷修复（P4 → P3 返工 → 复验）

独立评审（fresh-eyes 子代理，只给交接物与代码路径）对 `b72743a` 全部改动做了评审（`go build` / `go vet` / 全量 `go test ./internal/api/` / `go test ./internal/proxy/ -run 'Snat'` 均通过基础上的逐行审查），结论：**2 项必须修复 + 5 项 Nit**。

### M1：黑名单拒绝计数两处断链（必须修复，已修复复验）

- 现象：①目标黑名单多目标时 iptables 同 comment 有 N 条 DROP 行，`parseSnatCountersOutput` 对多行是**赋值而非求和**——只保留最后一条，其余 N-1 条目标的拒绝不计入；②`readSnatDropCounters` 只回传 PktsDrop、BytesDrop 被丢弃，全链路恒 0 → `pollSnatCounters` 差分恒 0 → denied 指标（列表 `denied_packets` / `/metrics`）**从不增长**。此前 per-rule DROP 移除后无 DROP 行所以未暴露，本功能恢复多行 DROP 后必现。
- 修复：`parseSnatCountersOutput` 同 comment 多行 ACCEPT/DROP 全部改为累加；`readSnatDropCounters` 改返回 `*snatCounters`，`ReadSnatCounters` / `readSnatCounters` 把 PktsDrop+BytesDrop 双字段接通。
- 复验（161，v7-test2）：双目标黑名单（172.16.30.0/24 + 172.16.40.1）分别试探，iptables 原始行计数 8 包 + 2 包，API `denied_packets=10` **精确等于两行之和**（修复前只会显示 8、且恒不增长）。

### M2：off 源模式 + 目标黑名单可落地为无源 DROP，跨规则误伤（必须修复，已修复复验）

- 现象：`validateSnat` 只要求 allow_list 非空但不禁止 `acl_mode=off`；引擎对非 whitelist 源整体清空 → 目标黑名单 DROP 行失去 `-s` 源匹配，变为「该网卡对上所有去往目标 X 的转发流量全丢」——不分源、不分规则，包括其他 SNAT 规则的白名单流量（v2 per-rule DROP 事故同型）。前端恒发 whitelist 不会触发，API 直调（curl/脚本/导入）可达。
- 修复（纵深防御两层）：API 层 `validateSnat` 拒绝 SNAT 的 off 源模式（与前端语义对齐，off+目标黑名单给专属错误文案）；引擎层 `buildSnatSpec` 黑洞兜底（`0.0.0.0/32`）条件扩到"目标黑名单非空"情形——即便直改库也绝不落地无源 DROP。
- 复验（161，v7-test2）：off 源 + 目标黑名单 → 400（专属文案）；off 源 + 带 allow → 400；off 源 + 无名单 → 400。单元测试新增断言：DROP 行必须带 `-s`（无源 DROP 防御的最终形态断言）。

### Nit（本批已修复 N1/N3/N4；N2/N5 记录不改）

- **N1 已修复**：`snatPurgeByComment` 盲拆 32 轮上限注释依据过时（目标黑名单 N 条目标 → 2+N 行），扩到 256 轮防御上限（N>250 由启动对账兜底）。
- **N3 已修复**：WebUI 目标模式切换不清空旧列表会在黑白名单语义完全相反时静默反转提交——切换时弹确认框（清空/保留）；tag 配色随模式（黑名单 danger / 白名单 success）。
- **N4 已修复**：前端 `IP_RE` 去掉 IPv6 分支，与后端 `isCIDROrIP`（IPv4-only）对齐，消掉"tag 能加、保存 400"的不一致（同款源名单输入框一并生效）。
- **N2 记录不改**（pre-existing）：`teardownArgs` 复用 `-I` 形态行导致拆除前先重插一遍再靠盲拆删（每次热更新多 2N 次无谓 iptables 执行）；正确性由盲拆兜底保证，属性能损耗非正确性问题。
- **N5 记录不改**（架构约束显式化）：目标白名单的"名单外拒绝"依赖 FORWARD 链尾 policy DROP；FORWARD policy 为 ACCEPT 的主机上目标白名单不生效（黑名单不受影响，显式 DROP 行）。161 生产形态 policy DROP 该前提成立。
